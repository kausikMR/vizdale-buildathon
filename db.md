# Temple CRM — Database Implementation Guide

This document defines how to implement the persistence layer described in
[`CONTRACT.md`](CONTRACT.md). The contract remains the source of truth for entity
shapes, statuses, API behaviour, and business rules. This guide only chooses the
database tooling and translates that contract into an implementation plan.

## 1. Stack and conventions

- PostgreSQL is the database.
- Use [Drizzle ORM](https://orm.drizzle.team/) for typed queries and relations.
- Use `drizzle-kit` for generated SQL migrations.
- Use the `postgres` driver (`postgres.js`) for database connections.
- Read the connection string from `DATABASE_URL`; never commit a real URL.
- Keep database column names in `snake_case`. Drizzle/TypeScript property names and
  API response fields use `camelCase`.
- Store timestamps as `timestamptz` and dates/times as native Postgres `date` and
  `time` values. Do not convert date-only values through JavaScript `Date` objects.

The root environment files should contain:

```dotenv
DATABASE_URL=postgresql://USER:PASSWORD@HOST:PORT/DATABASE
```

Add the same key with a non-secret placeholder to `.env.example`. The application
must fail fast on startup with a clear error if `DATABASE_URL` is absent.

## 2. Packages and scripts

Install runtime dependencies in the API workspace:

```bash
npm install -w api drizzle-orm postgres dotenv
npm install -D -w api drizzle-kit
```

Add these scripts to `apps/api/package.json`:

```json
{
  "scripts": {
    "db:generate": "drizzle-kit generate",
    "db:migrate": "tsx src/db/migrate.ts",
    "db:seed": "tsx src/db/seed.ts",
    "db:studio": "drizzle-kit studio"
  }
}
```

Suggested file layout:

```text
apps/api/
  drizzle.config.ts
  drizzle/                 generated SQL migrations, committed to git
  src/db/
    client.ts              connection and Drizzle instance
    schema.ts              tables, constraints, indexes, and relations
    migrate.ts             migration runner
    seed.ts                idempotent demo data
    repositories/          business-safe database operations
```

`drizzle.config.ts` should point to `src/db/schema.ts`, write migrations to
`drizzle/`, use the PostgreSQL dialect, and read `DATABASE_URL` from the repository
root `.env`. Runtime configuration must do the same, regardless of whether commands
are launched from the repository root or from `apps/api`.

Use one shared `postgres` client per API process. Export both the client and the
Drizzle `db` instance so graceful shutdown can call `client.end()`.

## 3. Schema

Implement all eight tables from §3 of [`CONTRACT.md`](CONTRACT.md):

1. `users`
2. `events`
3. `slots`
4. `bookings`
5. `prasadam_items`
6. `prasadam_orders`
7. `order_items`
8. `inventory_movements`

Use UUID primary keys with `gen_random_uuid()` defaults and `created_at` defaults of
`now()`. Implement the contract's foreign-key delete behaviour exactly. In
particular, deleting an event cascades to its slots, deleting an order cascades to
its order items, and deleting a prasadam item cascades to its inventory movements.

Statuses may be Postgres enums or text columns with `CHECK` constraints. Prefer
Postgres enums because Drizzle then exposes the allowed values to TypeScript. The
allowed values must exactly match §2 of the contract:

| Enum | Values |
|---|---|
| role | `devotee`, `admin` |
| user status | `active`, `inactive` |
| event status | `draft`, `published`, `completed`, `cancelled` |
| slot status | `open`, `closed` |
| booking status | `confirmed`, `cancelled` |
| order status | `confirmed`, `ready`, `fulfilled` |
| movement type | `reserve`, `release`, `restock`, `adjust` |

Keep the following invariants as database constraints, not only application
validation:

```text
events.end_date >= events.start_date
slots.end_time > slots.start_time
slots.capacity > 0
slots.booked_count >= 0
slots.booked_count <= slots.capacity
bookings.visitor_count > 0
bookings.visitor_count <= 6
prasadam_items.stock >= 0
prasadam_items.reorder_level >= 0
order_items.quantity > 0
```

Additional schema details:

- `bookings.attendee_details` is non-null `jsonb` with a default of `[]`.
- `display_price` is `numeric(10,2)` and informational only. No payment or payment
  state belongs in this schema.
- `bookings.reference` and `prasadam_orders.reference` are unique and generated by
  Postgres sequences using the `DSN-00001` and `PRS-00001` formats from the contract.
- Add a unique constraint on `order_items (order_id, item_id)` so one item cannot
  appear twice in the same order. Merge duplicate request lines before insertion.
- Do not add `cancelled_at` unless the open decision in §7 of the contract is
  explicitly resolved; the current schema contract does not define that column.

Define Drizzle relations for the foreign keys, but remember that relations only
help construct queries; the actual `.references(...)` declarations enforce
referential integrity in PostgreSQL.

### Indexes

Primary keys and unique references are already indexed. Add indexes for expected
joins and list filters:

```text
slots(event_id, date, start_time)
bookings(user_id, created_at)
bookings(slot_id, status)
prasadam_orders(user_id, created_at)
order_items(order_id)
order_items(item_id)
inventory_movements(item_id, created_at)
```

Avoid speculative indexes beyond these until query plans show a need.

## 4. Migrations

Generate and commit migrations whenever `schema.ts` changes:

```bash
npm run db:generate -w api
npm run db:migrate -w api
```

Do not run `drizzle-kit push` in shared or production environments: committed SQL
migrations provide a reviewable history. The API may run pending committed
migrations during local/demo startup, but it must not regenerate migrations or
destructively recreate tables on boot.

The initial migration must create `pgcrypto` if the target Postgres version needs
it for `gen_random_uuid()`, then create enums, sequences, tables, constraints, and
indexes in dependency order.

## 5. Seed data

`seed.ts` must create the fixed demo data from §6 of [`CONTRACT.md`](CONTRACT.md).
Use the documented UUIDs and references so frontend flows can rely on them. Dates
must be derived from the database's `CURRENT_DATE`, keeping the demo useful on any
day and in any server timezone.

Seeding must be idempotent:

- upsert fixed users, events, slots, and prasadam items by their fixed UUIDs;
- insert the sample booking and its dependent counts only when absent;
- never reset stock, booking counts, statuses, or user-created records on normal API
  startup;
- run the seed explicitly with `npm run db:seed -w api`.

Wrap the seed in a transaction so a failure cannot leave a partial dataset.

## 6. Transaction-safe business operations

Routes must not update counters or stock directly. Put the following operations in
repository/service functions and execute each operation in one database
transaction.

### Create a booking

1. Validate `visitorCount` and attendee data.
2. Confirm the event is `published` and the slot is open and not past.
3. Atomically reserve capacity with the guarded update from the contract:

```sql
UPDATE slots
SET booked_count = booked_count + $visitor_count
WHERE id = $slot_id
  AND status = 'open'
  AND capacity - booked_count >= $visitor_count
RETURNING *;
```

4. If no row is returned, query the slot in the same transaction to distinguish
   `SLOT_CLOSED`, `SLOT_PAST`, `EVENT_NOT_BOOKABLE`, and
   `INSUFFICIENT_CAPACITY`.
5. Insert the booking and commit.

Do not implement this as a read followed by an unconditional update; concurrent
requests could oversell the slot.

### Cancel a booking

Guard the status transition so capacity is restored exactly once:

```sql
UPDATE bookings
SET status = 'cancelled'
WHERE id = $booking_id AND status = 'confirmed'
RETURNING slot_id, visitor_count;
```

Only when a row is returned, decrement that slot's `booked_count` by the returned
visitor count in the same transaction. A second cancellation returns no row and
must not restore capacity again.

### Create a prasadam order

Reserve every order line inside one transaction. For each item, use a guarded
update:

```sql
UPDATE prasadam_items
SET stock = stock - $quantity
WHERE id = $item_id
  AND active = true
  AND stock >= $quantity
RETURNING id, display_price;
```

If any line returns no row, inspect that item to return `ITEM_INACTIVE` or
`INSUFFICIENT_STOCK`, then roll back the entire order. After each successful update,
insert an `inventory_movements` row with type `reserve` and a negative quantity.
Insert `order_items.display_price` from the value returned by the reservation, not
from client input.

Sort normalized order lines by `item_id` before reserving them. A consistent lock
order reduces deadlock risk when concurrent orders contain the same items.

### Adjust inventory

Use a guarded update that requires `stock + delta >= 0`. Insert exactly one
append-only movement in the same transaction. Use movement type `restock` for a
positive replenishment and `adjust` for other admin corrections; store the supplied
reason and acting admin in `created_by`.

Never update or delete historical `inventory_movements` records.

### Advance order status

Allow only `confirmed -> ready -> fulfilled`. Put the expected current status in the
`UPDATE ... WHERE` clause so concurrent requests cannot skip a state. Return
`STATUS_TRANSITION_INVALID` when no row is updated.

## 7. Query rules

Enforce visibility and ownership in database query functions, even when routes also
check them:

- devotees see only published events and bookable slots;
- devotees see only active prasadam items;
- devotee booking and order queries always include `user_id = signedInUserId`;
- admin queries may include all rows;
- never accept a devotee identity from a query parameter or request body.

Compute API-derived fields in SQL/query mappers:

- slot `remaining` and `bookable`;
- event `totalCapacity` and `totalBooked`;
- prasadam `lowStock` and `reservable`;
- booking event/slot/devotee display fields;
- order items and devotee name.

Return numeric prices consistently. The `postgres` driver commonly returns
`numeric` values as strings; either preserve that representation in the shared API
types or convert it deliberately in one mapper. Do not allow route-by-route
behaviour to differ.

## 8. Errors and observability

Repository functions should expose typed domain errors matching §5 of the contract.
Translate known Postgres failures as follows:

- check or enum violation -> `CONSTRAINT_VIOLATION` (HTTP 409);
- unique reference collision -> retry reference generation if appropriate, otherwise
  `CONSTRAINT_VIOLATION`;
- connection/configuration failures -> `INTERNAL_ERROR` (HTTP 500) and log the
  server-side cause without credentials.

Never include `DATABASE_URL`, SQL parameters containing personal data, or raw driver
errors in API responses. A health check should execute a lightweight query such as
`select 1`; report the service as unavailable when the database cannot be reached.

## 9. Verification checklist

The database layer is complete when all of the following pass against a migrated
Postgres database:

- migrations apply successfully to an empty database and are a no-op when rerun;
- the seed can be run twice without duplicates or resetting mutable demo state;
- a booking cannot exceed six visitors or make `booked_count > capacity`;
- two concurrent booking requests cannot oversell the same slot;
- cancelling the same booking twice restores capacity only once;
- an unpublished, completed, or cancelled event cannot be booked;
- a multi-item order rolls back completely if any item lacks stock;
- stock can never become negative;
- every stock change has a matching inventory movement;
- inactive items cannot be reserved;
- order statuses cannot skip or move backwards;
- devotee queries cannot read another devotee's bookings or orders;
- `npm run build -w api` succeeds with Drizzle's inferred types.

At minimum, integration tests should cover the concurrency and rollback cases with
the real Postgres database. Mocked unit tests cannot prove row-locking or constraint
behaviour.
